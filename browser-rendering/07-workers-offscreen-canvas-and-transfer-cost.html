Worker：收益边界、OffscreenCanvas 与通信成本

🔖本文约 847 字，阅读预计耗时 3 分钟。
ⓘAI 辅助写作声明：本文由博主构思逻辑，AI 辅助润色，双方共同校对。
2026年1月20日 ·更新于 2026年1月22日 ·study·🏷️ browser-rendering🏷️ webworker🏷️ offscreen-canvas🏷️ performance🏷️ structured-clone

很多团队把“上 Worker”当成性能优化的银弹：主线程忙？挪出去。问题是，这个动作只对一类成本有效——纯计算。而浏览器渲染链路里最硬的一部分（style/layout/paint/composite/raster）并不会因为你挪走 JS 就自动变快。

这一章的目标是把 Worker 的收益边界讲清楚，并说明 OffscreenCanvas 这条“让 Worker 参与画画”的路径为什么既强大又容易踩坑。

1. Worker 家族：别把它们当成一种东西 ​

  • Dedicated Worker：最常见，用于把计算挪出主线程
  • Shared Worker：多个页面共享（现实里少用，生态与限制更多）
  • Service Worker：偏网络/缓存/离线的中间层，不直接参与渲染

这里讨论的“性能优化上 Worker”，默认指 Dedicated Worker。

2. 结构化克隆（structured clone）：跨线程不是免费 ​

主线程与 Worker 通信的默认方式是 postMessage。它背后通常意味着：

  • 序列化/反序列化（structured clone）
  • 任务排队（消息队列）
  • 可能的拷贝（尤其大对象/深层对象）

因此一个典型反直觉是：你把计算挪到 Worker，但每帧把一大坨结果传回来，反而更卡。

2.1 Transferable：把“拷贝”变成“转移所有权” ​

对 ArrayBuffer 这类对象，Transferable 可以把成本从“拷贝”变成“所有权转移”。它通常更快，但带来新的约束：

  • 主线程发送后 buffer 在主线程侧会变“不可用”
  • 你需要设计好双缓冲/环形缓冲，避免频繁分配新 buffer

2.2 SharedArrayBuffer：共享带来速度，也带来治理成本 ​

SharedArrayBuffer 允许共享内存，配合 Atomics 可以做低延迟协作。但它受安全策略约束（例如 cross-origin isolation），并且需要更严谨的并发设计。

3. Worker 能解决什么：把“计算密集”与“渲染提交”拆开 ​

Worker 更擅长解决这些问题：

  • 大量纯计算：排版预处理、几何计算、数据解析、加密压缩、图像处理（取决于 API）
  • IO/解析：把大 JSON/二进制解析从主线程挪走（前提是传输与同步点可控）
  • 任务切片：把长任务拆成更小的片段，降低主线程被长时间占用的概率

Worker 不擅长解决这些问题：

  • DOM/CSSOM 相关：layout/paint 的硬成本不会消失
  • 频繁同步：每帧必须等 Worker 结果再继续（等待本身就是 jank 的根）

4. OffscreenCanvas：让 Worker 参与“画画”的少数路径 ​

OffscreenCanvas 的核心价值是：把某些绘制工作（尤其 canvas）放到 Worker 线程执行，让主线程不再承担绘制相关的 JS 成本。

但它的上限通常被三件事决定：

  • 你传输的数据量与频率（大图像/大顶点数组每帧传输会很贵）
  • 你是否引入了新的同步点（主线程等待 Worker 的帧结果）
  • GPU/栅格化是否已经是瓶颈（此时挪走 JS 收益会迅速变小）
sequenceDiagram
  participant Main as Main thread
  participant Worker as Worker
  participant GPU as GPU/Viz
  Main->>Worker: postMessage（输入/状态）
  Worker->>Worker: update + draw（OffscreenCanvas）
  Worker-->>GPU: submit（实现路径随平台/配置变化）
  GPU-->>Main: present（最终上屏）

5. 一个实用的判断题：你是在“挪走计算”，还是在“引入通信税” ​

我更愿意把 Worker 优化当成一个简单的算账题：

  • 省下来的：主线程计算时间
  • 新增的：消息传递/序列化/拷贝/同步等待

当新增的通信税超过省下来的计算，Worker 就会从优化变成退化。
