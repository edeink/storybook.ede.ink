输入与滚动：事件路由、命中与延迟下限

🔖本文约 789 字，阅读预计耗时 2 分钟。
ⓘAI 辅助写作声明：本文由博主构思逻辑，AI 辅助润色，双方共同校对。
2026年1月20日 ·更新于 2026年1月29日 ·study·🏷️ browser-rendering🏷️ chromium🏷️ input🏷️ latency🏷️ scrolling🏷️ hit-test🏷️ inp

用户感知延迟的本质是：输入发生在 t0，但系统直到 t1 才把“我理解你要干什么”的视觉反馈画出来。渲染链路再复杂，最终都要接受这个 KPI 的拷问。

这一章从 Chromium 视角把输入链路拆开：事件怎么从系统进入浏览器、怎么路由到目标 frame、怎么命中、滚动为什么尽量走合成线程，以及前端如何把延迟拆成可归因的部分。

1. 输入不是“一个事件”，而是一条跨进程管线 ​

粗粒度的链路可以画成这样：

flowchart LR
  OS["OS input<br/>touch/mouse/keyboard"] --> Browser["Browser process<br/>route + policy"]
  Browser --> Renderer["Renderer process<br/>main/impl/worker"]
  Renderer --> Blink["Blink<br/>dispatch + DOM events"]
  Blink --> JS["JS handlers<br/>framework scheduler"]
  JS --> Blink
  Blink --> CC["cc draw"]
  CC --> Viz["Viz present"]
  Viz --> Screen["screen"]

这里有两个容易忽略的事实：

  • 事件可能跨进程：尤其当目标 frame 在另一个 renderer
  • 事件可能跨线程：滚动、合成、raster 都可能不在 main thread 上跑

2. Hit testing：命中不是免费，它决定了“你点哪儿算哪儿” ​

命中（hit test）要回答的问题很朴素：一个坐标点落在谁身上？但在真实网页里它会遇到：

  • transform/clip/effect/opacity 叠加
  • 多层遮挡与 z-order
  • iframe 跨进程
  • 滚动偏移与滚动链

为了让命中足够快，系统会维护用于命中的数据结构，并在某些阶段更新它们。命中数据更新的时机，决定了交互延迟的下限：如果命中强依赖主线程最新布局，那主线程一忙你就会“点不动”。

3. 滚动：为什么浏览器宁愿复杂，也要把它从主线程搬走 ​

滚动有两个特性：

  • 高频：输入设备会持续产生滚动增量
  • 强反馈：每一帧都需要视觉更新

因此 Chromium 会尽量让滚动走 compositor thread（impl-thread scrolling）。前端看到的行为差异通常来自：

  • 能在合成线程处理的滚动：主线程忙也能滚
  • 必须等主线程的滚动：主线程一忙就卡住（常见原因是滚动链路需要主线程确认、或有阻塞性的事件处理）

4. INP/交互延迟：前端口径与底层拆分 ​

从前端度量看，像 INP（Interaction to Next Paint）这种指标，本质是在衡量：

  • 事件排队等待（main thread/renderer 忙导致）
  • 事件处理耗时（JS + DOM 事件分发 + 框架调度）
  • 结果上屏等待（style/layout/paint + composite + present）

在排障时建议把它拆成三段：

  1. 输入到 handler 开始：排队/路由开销
  2. handler 执行：JS/DOM 成本（以及是否触发强制同步）
  3. handler 结束到 next paint：渲染链路与同步点成本

5. 前端可操作的几个“延迟杀手” ​

  • 长任务：把一次交互处理拆成可中断的小块（或搬到 worker），减少 handler 阶段阻塞
  • 强制同步布局：避免在交互路径上读写交错（尤其是 pointermove/touchmove）
  • 滚动监听：谨慎对待会阻塞滚动的监听逻辑（必要时显式 passive: true），尽量让滚动走 compositor
  • 过度重绘：交互反馈尽量走合成友好路径，否则 next paint 会被 paint/raster 吞掉
